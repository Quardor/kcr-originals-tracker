# ARCHITECTURE — kcr-ml

Архитектурная документация kcr-ml — сервиса ИИ-помощника: назначение, use cases, стек,
слоистую архитектуру, контракт API (REST + WebSocket), модель подключения LLM, файловую структуру
и план внедрения. Документ — план продукта: следуя ему, получается ИИ-помощник, точно
соответствующий ТЗ («ТЗ: сервис контроля передачи оригиналов документов и коммуникации
с клиентами КЦР», сценарии 3–4, 12; критерии готовности MVP). Любое изменение архитектуры,
стека или структуры проекта **должно** отражаться в этом файле.

Контекст монорепозитория kcr-originals-tracker:

- `server/kcr-backend` — Spring Boot, единственный владелец данных (PostgreSQL): клиенты,
  срезы, события, претензии, аутентификация (JWT). Источник истины — его
  [ARCHITECTURE.md](../server/kcr-backend/ARCHITECTURE.md);
- `client/kcr-frontend` — SPA на React (Vite), потребляет REST/WebSocket этого сервиса
  наряду с API бэкенда;
- `ml/` (этот сервис) — Python/FastAPI: ИИ-помощник и аналитика. Этим закрывается открытый
  вопрос 5 §11.7 ARCHITECTURE.md бэкенда (где живёт LLM): **отдельным сервисом в `ml/`**,
  а не прокси-эндпоинтом бэкенда; запланированные там `POST /api/v1/ai/*` реализуются здесь,
  бэкенд трафик ИИ не проксирует.

Терминология: в ТЗ — «КЦР», в проектах закреплён латинский вариант KCR (`kcrCode`) — один и тот
же идентификатор клиента.

## 1. Инварианты продукта (из ТЗ)

Неизменяемые правила, которым подчинена вся архитектура:

1. **Read-only.** ИИ-помощник не изменяет данные, статусы, этапы работы и ответственных:
   решение всегда принимает сотрудник. В сервисе архитектурно нет мутирующих путей —
   источник данных доступен только на чтение (§4, §8).
2. **Только данные сервиса.** Ответы опираются исключительно на данные kcr-backend; список
   клиентов или число в ответе никогда не генерируется LLM «из головы» — только возвращается
   источником данных (§4, принцип «LLM формулирует — данные считает код»).
3. **Приёмка по контрольным сценариям.** Готовность проверяется сценариями из ТЗ (§14),
   они же — тесты приёмки в репозитории.
4. **Автономность.** Сервис разворачивается отдельно от внутренних систем Контура и работает
   поверх данных, уже загруженных в kcr-backend (обмен с Контуром — Excel на стороне бэкенда).

## 2. Акторы и use cases

Акторы — роли kcr-backend (`ADMIN`, `OPERATOR`), аутентификация — его же access-токенами
(§8). Администратор наследует возможности оператора.

| # | Use case | Актор | Триггер | Результат |
|---|---|---|---|---|
| UC-1 | Вопрос по данным (чат) | обе роли | сообщение в чате на естественном языке | streamed-ответ + при необходимости выборка данных для таблицы; примеры из ТЗ: «Покажи клиентов, которым пора позвонить повторно», «У кого количество непереданных документов не меняется несколько срезов подряд?», «Покажи клиентов, которым сегодня требуется внимание» |
| UC-2 | Краткая сводка перед звонком | оператор | открытие карточки клиента / запрос сводки | текущее состояние, динамика, последние контакты, договорённости, следующее действие + текстовая сводка |
| UC-3 | Приоритетная выборка | админ | свободно-формулированный запрос («не VIP, не передано > 25%, не в работе») | структурированные критерии + отсортированный список клиентов с баллами и обоснованием; список — предложение, включение в работу — отдельное решение админа |
| UC-4 | Данные для дашбордов | обе роли | открытие экрана аналитики на клиенте | JSON-агрегаты (серии, распределения, топы), готовые к отображению графиками на клиенте |
| UC-5 | Экспорт в Excel | админ | кнопка «выгрузить» у выборки/аналитики | xlsx-файл (openpyxl/pandas) |

Основной поток UC-1 (чат):

1. Клиент открывает WebSocket `/api/v1/ai/chat` (§7) и отправляет текст вопроса.
2. Сервис собирает контекст: системный промпт (роль, правила, доступные инструменты) +
   последние сообщения соединения (лимит конфигурацией).
3. LLM выполняет tool-calling цикл (≤ N итераций): вызывает инструменты чтения данных
   (поиск клиентов, карточка, история срезов, события, «сегодня нужно») — это методы
   порта источника данных поверх read-only API бэкенда, от имени текущего пользователя.
4. Ответ стримится клиенту порциями; при выборе данных дополнительно отправляется
   сообщение `data` (колонки + строки) для таблицы на клиенте.
5. Если вопрос вне данных сервиса или требует мутации — помощник отказывает (инвариант 1–2),
   отказ — тоже контролируемый ответ, а не ошибка протокола.

Основной поток UC-3 (приоритизация) — ключевой к анти-галлюцинациям:

1. Свободный текст → LLM **структурирует** в критерии (JSON-схема: фильтры полей, пороги,
   направление сортировки) — вывод валидируется Pydantic-схемой, невалидное — повтор/отказ.
2. Критерии применяет **детерминированный** код: фильтрация + скоринг (веса — конфигурация;
   факторы: доля непереданных, категория динамики, срочность следующего контакта, этап, VIP).
3. Ответ: критерии (машиночитаемо) + список `{kcrCode, название, балл, обоснование[]}` +
   текстовое пояснение от LLM поверх готового списка.

## 3. Архитектура: Clean Architecture / DDD

Цель (зафиксированное решение): **легко переписывать и видоизменять код**. Достигается слоями
с обязательным направлением зависимостей и портами/адаптерами: смена LLM, источника данных,
протокола доставки или Excel-библиотеки — новый адаптер, без правки бизнес-логики.

```
        ┌────────────────────────────────────────────┐
        │ api/            REST-роутеры + WebSocket    │  FastAPI, Pydantic-схемы
        └───────────────┬────────────────────────────┘
                        ▼
        ┌────────────────────────────────────────────┐
        │ application/    use-case'ы, оркестрация     │  chat / brief / prioritize /
        │                 + ports.py (Protocol-порты) │  analytics / export
        └──────┬──────────────────────────┬──────────┘
               ▼                          ▼
        ┌──────────────┐          ┌─────────────────────────────────┐
        │ domain/      │          │ infrastructure/ (адаптеры)       │
        │ чистый Python│◀—только— │ llm/  data/  excel/  security/   │
        │ правила,     │          │ реализуют порты application     │
        │ скоринг,     │          └─────────────────────────────────┘
        │ read-model   │
        └──────────────┘
```

Правила:

- `domain/` — чистый Python: сущности-представления (read-model клиента/срезов/событий),
  правила скоринга и критерии. Никаких импортов FastAPI, httpx, SDK LLM, pandas.
- `application/` — use-case'ы (§2). Зависят только от `domain/` и собственных портов
  (`ports.py`: `LlmPort`, `DataSourcePort`, `ExcelExporterPort` — `typing.Protocol`).
  Ничего не знают о HTTP, WebSocket и конкретном провайдере LLM.
- `infrastructure/` — адаптеры, реализуют порты: `llm/` (OpenAI-совместимый клиент — и API,
  и локальный Qwen, §5), `data/` (httpx-клиент kcr-backend, только GET), `excel/`
  (openpyxl/pandas), `security/` (валидация JWT).
- `api/` — доставка: REST-роутеры, WebSocket-эндпоинт, Pydantic-схемы. Тонкий: принял схему →
  вызвал use-case → вернул схему.
- Подстановки без правки ядра: тесты — фейки портов; LLM API ↔ локальный Qwen — настройка
  окружения (§5); источник данных REST ↔ другой транспорт — новый адаптер `DataSourcePort`.
- **Read-only enforced кодом:** `DataSourcePort` содержит только читающие методы; адаптер
  `data/` выполняет только `GET`-запросы. Мутаций нет ни на одном слое — инвариант 1 §1.

## 4. Технологический стек

| Компонент | Технология |
|---|---|
| Язык | Python ≥ 3.12 |
| Пакетный менеджер | **uv** (`uv.lock` в git; никаких pip/poetry) |
| Веб-фреймворк | **FastAPI** + uvicorn (standard) |
| Валидация и конфигурация | Pydantic v2 + pydantic-settings |
| HTTP-клиент к бэкенду | httpx (async) |
| LLM-клиент | OpenAI-совместимый (SDK `openai`, наводится на любой `base_url`; tool calling) |
| Аутентификация | проверка access-токенов kcr-backend: HS256, общий секрет (PyJWT) |
| Excel | **openpyxl** (создание/правка книг) + **pandas** (агрегации → листы) — готовые решения, своя реализация парсинга xlsx не пишется |
| Линтер и форматтер | **ruff** (lint + format, конфигурация в `pyproject.toml`) |
| Тесты | pytest + pytest-asyncio (+ fakes портов, ASGI-клиент httpx) |
| Контейнер | Docker (multi-stage Dockerfile, §12) |

Точные версии фиксируются `uv.lock`; в `pyproject.toml` — нижние границы.

## 5. LLM: универсальное подключение (API и локальный Qwen)

Зафиксированное решение: **в проде LLM работает локально (Qwen), на этапе тестов — по API**.
Переключение — настройкой окружения, без правки кода: практически все провайдеры
(облачные API и локальные серверы **vLLM**/**Ollama**, поднимающие модели Qwen) говорят
на OpenAI-совместимом протоколе `/v1/chat/completions`.

- `LlmPort` (application): `chat_stream(messages, tools) -> AsyncIterator[события]` —
  единый контракт стриминга и tool calling для всех use-case'ов.
- `infrastructure/llm/openai_compat.py` — единственный адаптер для обоих режимов:
  - `LLM_PROVIDER=api` — облачный провайдер (для тестов; `LLM_BASE_URL` + `LLM_API_KEY`);
  - `LLM_PROVIDER=local` — Qwen, поднятый vLLM или Ollama (`LLM_BASE_URL=http://…:11434/v1`,
    ключ не нужен, `LLM_MODEL=qwen…`).
- `infrastructure/llm/factory.py` — выбор адаптера по настройкам. Новый провайдер
  с иным протоколом = новый адаптер `LlmPort` + строка в factory; use-case'ы не меняются.
- Инструменты tool calling — это методы `DataSourcePort`; LLM не получает ни HTTP-доступа,
  ни SQL — только описанные декларативно функции чтения (см. §7: какие данные бэкенда
  используются). Результаты инструментов попадают в контекст модели как есть — ответ
  опирается только на них.
- Локальный стенд: `docker-compose.yml` с сервисом ollama/vLLM (profile `local`) — модель
  Qwen поднимается рядом для разработки без внешних API.

## 6. Работа с Excel

Требование: для чтения и изменения Excel-таблиц использовать готовые решения — openpyxl
и pandas; собственный парсер xlsx не пишется. Применения в kcr-ml:

- **Экспорт (основное):** выгрузка выборок (UC-3) и аналитических отчётов (UC-4) в xlsx —
  pandas считает таблицу из read-model, openpyxl оформляет книгу (заголовки, ширины колонок);
  отдаётся файлом через REST (§7).
- **Чтение (по необходимости):** заранее подготовленные файлы-выгрузок/отчётов —
  через pandas.read_excel. Импорт клиентов и срезов **не дублируется**: он остаётся
  в kcr-backend (Apache POI, единая точка входа данных по ТЗ).
- Всё живёт в `infrastructure/excel/` за портом `ExcelExporterPort` — смена библиотеки
  не затрагивает use-case'ы.

## 7. Контракт API

Префикс `/api/v1/ai/**` (внутри — собственный origin сервиса; фронт зовёт kcr-ml напрямую,
CORS — §8). Аутентификация — Bearer access-токен kcr-backend, кроме `GET /health`.

### REST

| Метод и путь | Назначение |
|---|---|
| `GET /health` | liveness (без аутентификации) |
| `GET /api/v1/ai/clients/{id}/brief` | UC-2: данные для сводки + текст сводки LLM |
| `POST /api/v1/ai/prioritize` | UC-3: `{prompt, limit?}` → критерии + список с баллами |
| `GET /api/v1/ai/analytics/summary` | UC-4: счётчики — категории динамики, этапы, долги |
| `GET /api/v1/ai/analytics/dynamics` | UC-4: серии по отчётным периодам (для графиков во времени) |
| `GET /api/v1/ai/analytics/top-debt` | UC-4: топ клиентов по доле непереданных |
| `GET /api/v1/ai/analytics/operators` | UC-4: нагрузка операторов (в работе / сегодня к контакту) |
| `POST /api/v1/ai/export/xlsx` | UC-5: `{kind, table?}` → xlsx-файл; `kind` = `table` (готовая таблица с клиента: колонки + строки), `analytics_summary`, `analytics_dynamics`, `analytics_top_debt`, `analytics_operators` (пересчитываются детерминированно) |

Формат аналитики — готовые серии под графики клиента, например `GET /analytics/dynamics`:

```json
{
  "series": [
    {"period": "1 кв. 2026", "no_debt": 120, "first_occurrence": 14, "decreasing": 22,
     "unchanged_or_growing": 9, "reappeared": 4, "persistent": 11, "newcomer_risk": 3}
  ],
  "generated_at": "2026-11-08T10:00:00Z"
}
```

Категории динамики и их имена — едины с бэкендом (`DynamicsCategory`, §11.2 его
ARCHITECTURE.md). Источник агрегатов — read-only API бэкенда (справочник клиентов с фильтрами,
срезы); суммирование выполняется на стороне kcr-ml. Пока в бэкенде нет миграции V11
(колонка `dynamics_category`), категории вычисляются в kcr-ml детерминированно из истории
срезов (`domain/dynamics.py`, правила §11.2; приоритет категорий при пересечении правил —
см. docstring модуля). При росте объёмов — агрегатные эндпоинты
в бэкенде за тем же портом `DataSourcePort` (замена адаптера, ядро не меняется).

### WebSocket — чат с ИИ (UC-1)

`WS /api/v1/ai/chat?token=<access-токен>` (браузер не позволяет заголовок Authorization
в WS; компромисс MVP — токен в query, см. §8). Протокол сообщений — JSON, каждая строка
обязана иметь `type`; все сообщения валидируются Pydantic-схемами, невалидные закрывают
соединение с `error`.

Клиент → сервер:

```json
{"type": "user_message", "content": "Покажи клиентов, которым пора позвонить повторно"}
```

Сервер → клиент:

| `type` | Назначение |
|---|---|
| `assistant_delta` | порция сгенерированного текста (стриминг ответа) |
| `tool_status` | «запрашиваю данные…» — индикация вызова инструмента (имя) |
| `data` | выборка для таблицы на клиенте: `{title, columns[], rows[][]}` — числа и строки из источника, не из LLM |
| `assistant_done` | ответ завершён (id сообщения, итоговые токены) |
| `error` | `{code, message}` — контракт как у REST-ошибок |

История диалога — в памяти соединения, ограничение `AI_CHAT_HISTORY_LIMIT` последних
сообщений; переподключение начинает новую сессию (персистентность истории — открытый
вопрос, §15).

### Контракт ошибок

Единый JSON-контракт, повторяющий стиль kcr-backend:

```json
{ "code": "LLM_TIMEOUT", "message": "LLM provider did not respond in time", "timestamp": "2026-11-08T10:00:00Z" }
```

Коды — константы приложения (`AUTHENTICATION_REQUIRED`, `ACCESS_DENIED`, `VALIDATION_FAILED`,
`RESOURCE_NOT_FOUND`, `BACKEND_UNAVAILABLE`, `LLM_TIMEOUT`, `LLM_UNAVAILABLE`,
`LLM_INVALID_RESPONSE`, `TOOL_LIMIT_EXCEEDED`, `INTERNAL_ERROR`); доменные исключения маппятся
в HTTP-статусы единым обработчиком, непредвиденное — catch-all 500 с нейтральным телом.
Формат ответов REST — camelCase (как у бэкенда); внутри серий `analytics/dynamics` ключи
категорий — канонические имена `DynamicsCategory` в lower_snake_case (пример выше).

## 8. Аутентификация и безопасность

- kcr-ml **не выдаёт** токены: проверяет access-токены kcr-backend — HS256, тот же секрет
  (`AUTH_JWT_SECRET` = `jwt.secret` бэкенда, только из окружения), те же claims
  (`sub`, `roles`). Роли используются для UC-доступа (prioritize/export — админ).
- Проверенный токен **пробрасивается в kcr-backend как есть**: права на данные считает
  бэкенд — оператор видит своё, админ всё, дублирования правил доступа в kcr-ml нет.
- WebSocket: токен в query-параметре (попадает в логи прокси — принятый компромисс MVP;
  прод-опция — одноразовый ticket: REST выдаёт короткоживущий ключ, WS принимает его).
- CORS: только origin фронтенда (`APP_CORS_ALLOWED_ORIGINS`, dev — `http://localhost:5173`).
- Секреты — только окружение/`.env` (в git не попадает, шаблон `.env.example`).
- Лимиты защиты: таймаут LLM, максимум итераций tool-цикла (`AI_MAX_TOOL_ITERATIONS`),
  лимит истории, ограничение размера выборки в ответе. Токены и секреты не логируются.

## 9. Валидация данных

Pydantic v2 — на всех границах, невалидное отвергается сразу:

- REST: request/response-схемы; FastAPI отдаёт 400/422 с контрактом §7.
- WebSocket: каждая входящая/исходящая строка — схема; брак закрывает соединение с `error`.
- Конфигурация: `pydantic-settings` — при старте (fail-fast: неверный `LLM_PROVIDER`,
  пустой обязательный секрет — отказ запуска).
- Ответы LLM, используемые как данные (критерии UC-3): structured output → Pydantic-схема;
  невалидная структура — повторный запрос модели, затем отказ `LLM_INVALID_RESPONSE`,
  но никогда не «применить как есть».
- Ответы бэкенда (httpx) — схемы read-model; расхождение контракта — явная ошибка
  `BACKEND_UNAVAILABLE`, а не тихие частичные данные.

## 11. Инструменты и качество

- **uv** — единственный пакетный менеджер: `uv sync` (окружение из `uv.lock`),
  `uv run …` для всех команд; прямые `pip install` в окружении проекта запрещены.
- **ruff** — линтер и форматтер одновременно (конфигурация в `pyproject.toml`,
  line-length 120): `uv run ruff check . --fix`, `uv run ruff format .`. Аннотации типов
  обязательны (правило ruff).
- **pytest** — unit (фейки портов), integration (ASGI), scenarios (приёмка ТЗ).
- Запуск разработки (нужны `.env`, kcr-backend на `KCR_BACKEND_BASE_URL`):
  `uv run uvicorn kcr_ml.main:app --reload` — порт 8000.

## 12. Dockerfile

Multi-stage, воспроизводимый, без сборочных инструментов в рантайме:

1. `FROM python:3.12-slim AS deps` + `COPY --from=ghcr.io/astral-sh/uv:latest /uv /usr/local/bin/uv`
   → `uv sync --frozen --no-dev` (зависимости из `uv.lock`, без dev-пакетов);
2. `FROM python:3.12-slim` — копируются только `.venv` и `src/`; непривилегированный
   пользователь; `CMD ["uvicorn", "kcr_ml.main:app", "--host", "0.0.0.0", "--port", "8000"]`;
3. конфигурация — только переменными окружения (секретов в образе нет);
   `docker-compose.yml` поднимает app (8000) и, с `--profile local`, ollama/vLLM с Qwen.

## 14. Контрольные сценарии приёмки (из ТЗ)

Каждый — тест в `tests/scenarios/` с фиксированными данными; LLM на сценариях —
детерминированная заглушка (сравниваются вызовы инструментов и структура ответа),
живая модель прогоняется вручную по тем же сценариям.

1. «Покажи клиентов не VIP, у которых не передано больше 25% документов и которые ещё
   не находятся в работе» — выборка совпадает с ручным фильтром.
2. «У кого количество непереданных документов не меняется несколько срезов подряд?» —
   категория `UNCHANGED_OR_GROWING`/`PERSISTENT`.
3. «У кого после завершения предыдущего цикла снова появились непереданные документы?» —
   `REAPPEARED`.
4. «Покажи клиентов, которым сегодня требуется внимание / пора позвонить повторно» —
   `next_contact_at <= сегодня`.
5. Сводка перед звонком: состояние, динамика, последние контакты, договорённости,
   следующее действие — все числа из данных бэкенда.
6. Приоритетная выборка по нескольким признакам — критерии соответствуют тексту запроса.
7. Негативные: вопрос вне данных сервиса → отказ со ссылкой на доступные данные;
   просьба изменить данные/этап/ответственного → отказ (read-only), мутаций не происходит.

## 15. Порядок внедрения

1. **Каркас**: uv-проект, ruff, config, `/health`, Dockerfile + compose → зелёные проверки.
2. **Аутентификация** (JWT kcr-backend) + `DataSourcePort` на httpx (клиенты, срезы,
   события, worklist — read-only API бэкенда).
3. **Аналитика** (UC-4, без LLM): REST-агрегаты для дашбордов — первая польза клиента.
4. **Prioritize** (UC-3): `LlmPort` + OpenAI-совместимый адаптер (режим `api`),
   детерминированный скоринг в domain.
5. **Brief** (UC-2).
6. **Чат** (UC-1): WebSocket, tool-цикл, стриминг.
7. **Excel-экспорт** (UC-5): openpyxl/pandas.
8. **Локальный Qwen** (vLLM/Ollama, `LLM_PROVIDER=local`), контрольные сценарии §14,
   лимиты/таймауты.

Каждый пункт — ветка `feature/*` и PR в `develop` (конвенция монорепозитория); тесты
пишутся вместе с кодом, закрытые пункты переносятся из §15 в краткую заметку о состоянии
в README.
