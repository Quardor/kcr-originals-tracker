# AGENTS.md — правила работы агентов в kcr-backend

Файл в git (до 2026-11-07 игнорировался `.gitignore`) — рабочая инструкция агентов.

## 0. Обязательный первый шаг

**Перед выполнением ЛЮБОЙ задачи в этом проекте прочитай [ARCHITECTURE.md](./ARCHITECTURE.md) целиком.**
Он содержит назначение проекта, стек, архитектуру, доменную модель, схему аутентификации и текущее
состояние кода. Действия, противоречащие ARCHITECTURE.md, запрещены.

Если твоя работа меняет архитектуру, стек, доменную модель или состояние проекта —
**обнови соответствующие разделы ARCHITECTURE.md** в том же изменении.

## 1. Единая парадигма

Проект организован по package-by-feature (§3/§11.5 ARCHITECTURE.md): домены — feature-пакеты
(`auth/`, `clients/`, `snapshots/`, `imports/`, `users/`), кросс-доменный код — `common/`
(включая `common/error/` — контракт ошибок и `common/validation/` — правила формата
ИНН/КПП/кода KCR), инфраструктура — `security/` и `config/`. Внутри домена: контроллер и
сервисы — в корне пакета домена, `model/`, `repository/`, `dto/` — его подпакеты; вложенная
под-домена (`clients/events/`) — по той же схеме. Правила слоёв прежние:

- **контроллер (в корне домена)** — только транспортный слой: принять DTO → вызвать один метод
  сервиса → вернуть DTO + HTTP-статус. Никакой бизнес-логики, никакого обращения к
  repository/security напрямую.
- **сервис (в корне домена)** — вся бизнес-логика. Сервис не знает про HTTP: ни `HttpStatus`,
  ни `HttpServletRequest` внутри сервисов недопустимы. Ошибки сообщаются через
  `DomainException(ErrorCode)` (`common/error/`, §6 ARCHITECTURE.md).
- **model/** — JPA-сущности и enum'ы предметной области. Сущности не ссылаются на DTO и сервисы.
- **repository/** — только Spring Data интерфейсы. Принимают и возвращают **сущности** (`model/`),
  никогда DTO. Составные запросы — именованные методы, при невозможности — `@Query`.
- **dto/** — контракт API домена. Сущности наружу не отдаются никогда: маппинг entity ↔ DTO
  выполняется на границе (в контроллере или отдельном маппере, если станет объёмным).
- **Направление зависимостей между доменами** — только по схеме §3 ARCHITECTURE.md
  (`security → users`, `auth → users, security`, `clients → snapshots`,
  `imports → clients, snapshots`); `common` не импортирует ничего из доменных пакетов.
- Новый код кладётся в пакет своего домена; новый домен заводится по той же схеме
  (существительное в единственном числе: `ai/` и т.п.), а не `utils`/`helpers`.
- Одна сущность/сервис/контроллер/DTO — один файл. Имя файла = имя класса.

## 2. Оформление кода

### Форматирование
- Java 17; отступ — 4 пробела; скобки в стиле Алмана ( `{` на новой строке); файл в кодировке UTF-8.
- Ширина строки — до 120 символов; длинные списки аргументов переносятся как в существующем коде
  (по одному аргументу на строку).
- Пустая строка между объявлением пакета, импортами и классом (как в текущих файлах).
- Импорты — явные, без `import foo.*` (кроме `jakarta.persistence.*` / `lombok.*` в сущностях —
  так уже принято в проекте).

### Именование
- Классы/интерфейсы — `PascalCase`; методы, поля, переменные — `camelCase`; константы — `UPPER_SNAKE_CASE`.
- Имена отражают тип и назначение: поле `UserRepository userRepository`, а не транслит или
  названия из другой доменной сущности (не `personRepository` для `UserRepository`).
- Суффиксы обязательны: `…Service`, `…Controller`, `…Repository`, `…Exception`, `…Request`, `…Response`.
- Сообщения исключений и тексты в коде — на английском.

### DTO
- DTO — только Java `record`.
- Request-DTO — чистый record; валидация (jakarta.validation) — аннотациями на компонентах record'а.
- Response-DTO — record + Lombok `@Builder` (см. `AuthResponse`).
- Поля record'а — в том же порядке, что и поля запроса/ответа в API.

### Сущности (model/)
- Аннотации Lombok — одной строкой над классом: `@Getter @Setter @AllArgsConstructor @NoArgsConstructor @Builder`.
- Обязательно `@Entity` + `@Table(name = "snake_case_table")`.
- Идентификатор: `@Id @GeneratedValue(strategy = GenerationType.IDENTITY)`, тип `long`.
- Связи — с явным `fetch` (по умолчанию `LAZY` для `@ManyToOne`) и явными атрибутами
  (`nullable`, `unique`, `name` для колонок, отличных от camelCase).

### Внедрение зависимостей
- Только конструкторное внедрение через Lombok `@RequiredArgsConstructor`; поля — `private final`.
- Полевое внедрение (`@Autowired` на поле) и `new` для компонентов Spring запрещены.
- Бины инфраструктуры (кодировщики, ключи, менеджеры) объявляются в `config/`, а не в сервисах.

### Исключения (см. §6 ARCHITECTURE.md)
- Иерархия сведена к единственному доменному исключению: сервисы бросают
  `DomainException(ErrorCode)`; новое поведение ошибки — новая константа `ErrorCode`
  («код, HTTP-статус, сообщение по умолчанию») в `common/error/`, а не новый класс исключения.
- Сообщение ошибки — часть `ErrorCode`, человекочитаемое, без логов и стеков.

### Прочее
- Не оставлять закомментированный код и `TODO` без пояснения задачи.
- Секреты (jwt.secret, пароли БД) не хардкодятся в новых местах: только `application.properties`
  / переменные окружения; в коде — через `@Value` или `@ConfigurationProperties`.
- Логи — через SLF4J; `System.out.println` / `printStackTrace` запрещены.

## 3. Принципы ООП

### Инкапсуляция
- Поля классов — `private`; доступ наружу — через геттеры (Lombok `@Getter`), мутация — только там,
  где она реально нужна (`@Setter` осознанно: у DTO его нет вовсе, у сущностей есть — для JPA).
- Внутреннее состояние не раскрывается: наружу отдаются копии/DTO, а не ссылки на внутренние коллекции.

### Наследование
- Наследование используется только там, где есть настоящая is-a связь и переиспользование
  полиморфного поведения: иерархия исключений (`HttpException` → конкретные статусы), адаптация
  Spring-интерфейсов (`CustomUserDetailsService implements UserDetailsService`).
- Наследование ради переиспользования кода запрещено — для этого композиция (см. ниже).
- Сущности не наследуют друг друга без отображения в JPA-стратегию (`@MappedSuperclass` и т.п.).

### Полиморфизм
- Общий код зависит от абстракции и не ветвится по конкретным типам: `GlobalExceptionHandler`
  ловит `HttpException` и получает статус полиморфно через `getHttpStatus()` —
  новый тип исключения обрабатывается без правки хендлера. Поддерживай этот принцип:
  вместо `switch` по типу добавляй поведение в сам тип.
- Работа с Security-контрактом — через интерфейсы Spring (`UserDetailsService`,
  `PasswordEncoder`, `AuthenticationManager`), а не через конкретные классы.

### Композиция и SOLID
- **SRP**: один класс — одна ответственность и одна причина для изменения. Сервис разросся
  на несколько зон ответственности — выдели отдельный сервис (`AuthService`/`RefreshTokenService`).
- **OCP**: новое поведение добавляется новым классом/исключением/бином, а не правкой
  ветвлений в существующем коде.
- **LSP**: подтип (новое исключение, реализация интерфейса) обязан корректно выполнять контракт
  базового типа — включая `getHttpStatus()` и семантику сообщений.
- **ISP**: интерфейсы узкие по назначению; «толстые» интерфейсы ради одного метода не создаются.
- **DIP**: верхние слои зависят на абстракции (интерфейсы Spring, `SecretKey`), конкретики —
  только в `config/`.
- Композиция предпочтительнее наследования: сервисы получают зависимости через конструктор,
  а не расширяют базовые классы с логикой.

## 4. Безопасность (обязательные инварианты)

- Пароли — только BCrypt-хеш; открытые пароли не логируются и не попадают в DTO-ответы.
- Новые эндпоинты по умолчанию считаются защищёнными; публичными (`permitAll`) объявляются
  только маршруты аутентификации `/api/auth/**`.
- Проверки прав — `@PreAuthorize("hasRole('…')")` по enum `Role` (`ADMIN`, `OPERATOR`).
- Секреты и сроки жизни токенов — только из конфигурации (`jwt.*`).

## 5. Проверка перед завершением работы

1. `./gradlew build` (или минимум `./gradlew test`) — успешно; если проект не собирался до тебя —
   не ухудшай состояние и явно сообщи об этом.
2. Новые классы лежат в правильных пакетах, имена соответствуют §2, зависимостей между слоями
   в обратную сторону нет (§1).
3. Если изменены архитектура/модель/стек — ARCHITECTURE.md обновлён (§0).
4. В итоговом ответе перечисли изменённые файлы и результат сборки/тестов честно, без приукрашивания.
