## 1. Единая парадигма

Проект организован по package-by-feature (§3/§11.5 ARCHITECTURE.md): домены — feature-пакеты
(`ai/`, `auth/`, `clients/` с под-доменом `clients/events/`, `snapshots/`, `imports/`,
`users/`), кросс-доменный код — `common/` (включая `common/error/` — контракт ошибок и
`common/validation/` — правила формата ИНН/КПП/кода KCR), инфраструктура — `security/` и
`config/`. Внутри домена:
контроллер и сервисы — в корне пакета домена, `model/`, `repository/`, `dto/` — его подпакеты.
Исключение: в `clients/events/` сущности, enum'ы и репозитории лежат прямо в пакете (без `model/`
и `repository/`) — новый код там следует класть по тому же правилу, чтобы не плодить два стиля.
Правила слоёв:

- **контроллер (в корне домена)** — только транспортный слой: принять DTO → вызвать один метод
  сервиса → вернуть DTO + HTTP-статус. Никакой бизнес-логики, никакого обращения к
  repository/security напрямую.
- **сервис (в корне домена)** — вся бизнес-логика. Сервис не знает про HTTP: ни `HttpStatus`,
  ни `HttpServletRequest` внутри сервисов недопустимы. Ошибки сообщаются через
  `DomainException(ErrorCode)` (`common/error/`, §6 ARCHITECTURE.md).
- **model/** — JPA-сущности и enum'ы предметной области. Сущности не ссылаются на DTO и сервисы.
- **repository/** — только Spring Data интерфейсы. Принимают и возвращают **сущности** (`model/`),
  никогда DTO. Составные запросы — именованные методы, при невозможности — `@Query`.
- **dto/** — контракт API домена. Сущности наружу не отдаются никогда: маппинг entity ↔ DTO
  выполняется на границе (фабрика `from(entity)` в самом record'е либо отдельный маппер, если
  станет объёмно).
- **Направление зависимостей между доменами** — по фактической схеме §3 ARCHITECTURE.md:
  `ai → security, common`; `auth → users, security`; `security → users`;
  `clients → snapshots, users`; `snapshots → clients.model` (только `Client`);
  `imports → clients, snapshots, users.model`; `config → security, ai` (регистрация
  WebSocket-хендлера чата). Новую зависимость между доменами заводить только по этой схеме;
  цикл `clients ↔ snapshots` — известный долг (п. 62 §10), не углублять его.
- Новый код кладётся в пакет своего домена; новый домен заводится по той же схеме
  (существительное в единственном числе), а не `utils`/`helpers`.
- Одна сущность/сервис/контроллер/DTO — один файл. Имя файла = имя класса.

## 2. Оформление кода

### Форматирование
- Java 17; отступ — 4 пробела; скобки в стиле Аллмана ( `{` на новой строке); файл в кодировке UTF-8.
  Правило действует для нового кода; в существующем коде встречается и K&R (перечень — п. 60 §10
  ARCHITECTURE.md) — не смешивать стили внутри одного файла и не переформатировать чужой файл
  без необходимости.
- Ширина строки — до 120 символов; длинные списки аргументов переносятся как в существующем коде
  (по одному аргументу на строку).
- Пустая строка между объявлением пакета, импортами и классом (как в текущих файлах).
- Импорты — явные, без `import foo.*` (кроме `jakarta.persistence.*` / `lombok.*` в сущностях —
  так уже принято в проекте); без импортов классов собственного пакета.

### Именование
- Классы/интерфейсы — `PascalCase`; методы, поля, переменные — `camelCase`; константы — `UPPER_SNAKE_CASE`.
- Имена отражают тип и назначение: поле `UserRepository userRepository`, а не транслит или
  названия из другой доменной сущности (не `personRepository` для `UserRepository`).
- Суффиксы обязательны: `…Service`, `…Controller`, `…Repository`, `…Request`, `…Response`,
  `…Exception` (последний — только для `DomainException`; новых классов исключений не заводить).
- Сообщения исключений (`ErrorCode.message`) и тексты проблем импорта (`ParseIssue.message`) — на английском.

### Комментарии
- Комментарии в коде запрещены — любые: `//`, `/* … */`, Javadoc, `#`, `--`; в том числе
  закомментированный код, `TODO`/`FIXME` и пояснения над методом. Правило действует для
  `src/main/java`, `src/test/java`, новых SQL-миграций, `Dockerfile` (кроме директивы `# syntax=…`
  в первой строке) и `application*.yaml`.
- Назначение кода объясняют имена — класса, метода, переменной, тест-метода. Если без комментария
  непонятно, переименуй или выдели метод с говорящим именем, а не комментируй.
- Почему код написан именно так и какое правило он реализует — в ARCHITECTURE.md: доменная модель,
  инварианты и хронология §9 уже описывают большую часть причин; если пояснения там нет — допиши
  документ, а не код.
- Не редактируются по объективным причинам: применённые миграции `V1`–`V12` (контрольные суммы
  Flyway; новые миграции пишутся без комментариев), `gradlew`/`gradlew.bat` (генерируются Gradle),
  `.env.example` (пояснения к переменным — содержание этого файла), `.gitignore` (служебные
  заголовки Spring Initializr).

### DTO
- DTO — только Java `record`.
- Request-DTO — чистый record; валидация (jakarta.validation) — аннотациями на компонентах record'а.
  Нормализация значений (trim, регистр) — в компакт-конструкторе, до Bean Validation.
- Response-DTO — record + Lombok `@Builder` (см. `AuthResponse`).
- Поля record'а — в том же порядке, что и поля запроса/ответа в API.
- Поля-ссылки (`recordUrl` и подобные) проверяются на схему `http(s)://` — произвольные схемы
  в `href` не должны попадать в интерфейс (п. 48 §10).

### Сущности (model/)
- Аннотации Lombok — одной строкой над классом: `@Getter @Setter @AllArgsConstructor @NoArgsConstructor @Builder`.
- Обязательно `@Entity` + `@Table(name = "snake_case_table")`.
- Идентификатор: `@Id @GeneratedValue`, тип `Long`. Стратегия: `IDENTITY` — по умолчанию для
  небольших таблиц; `SEQUENCE` с `allocationSize = 50` — там, где нужны батчевые вставки
  (`clients`, `client_events`, `document_transfer_snapshots`; миграции `V12`, `V13`). У таблицы
  должен быть ровно один генератор id: переводя таблицу с `IDENTITY` на sequence, в той же миграции
  сними IDENTITY и поставь колонке `DEFAULT nextval('<sequence>'::regclass)`; sequence заводи
  с `MINVALUE 0` (иначе `setval(…, 0)` падает на пустой таблице) и пересинхронизируй счётчик
  с `MAX(id)` (п. 38 §10).
- Связи — с явным `fetch` (по умолчанию `LAZY` для `@ManyToOne`) и явными атрибутами
  (`nullable`, `unique`, `name` для колонок, отличных от camelCase).
- enum'ы в БД — `@Enumerated(EnumType.STRING)`, varchar + CHECK-список значений в миграции;
  расширение справочника — новая миграция с заменой CHECK.

### Внедрение зависимостей
- Только конструкторное внедрение через Lombok `@RequiredArgsConstructor`; поля — `private final`.
- Полевое внедрение (`@Autowired` на поле) и `new` для компонентов Spring запрещены.
- Бины инфраструктуры (кодировщики, ключи, менеджеры) объявляются в `config/`, а не в сервисах.

### Исключения (см. §6 ARCHITECTURE.md)
- Иерархия сведена к единственному доменному исключению: сервисы бросают
  `DomainException(ErrorCode)`; новое поведение ошибки — новая константа `ErrorCode`
  («код, HTTP-статус, сообщение по умолчанию») в `common/error/`, а не новый класс исключения.
- Сообщение ошибки — часть `ErrorCode`, человекочитаемое, без логов и стеков.

### Системные события истории
- Любая мутация клиента оставляет запись в истории (`ClientEventService.record`), автор —
  текущий пользователь. Тексты системных событий (поле `comment` записи) — на русском и
  рассчитаны на чтение оператором: русские подписи значений справочников, а не имена enum («Этап:
  в общем пуле → первый звонок», а не «Этап: IN_POOL → FIRST_CALL»).

### Миграции
- Применённые файлы `db/migration/V<n>__*.sql` не редактируются — любое изменение схемы
  в новую миграцию со следующим номером.

### Прочее
- Секреты (jwt.secret, пароли БД) не хардкодятся в новых местах: только `application*.yaml` /
  переменные окружения; в коде — через `@Value` или `@ConfigurationProperties`.
- Логи — через SLF4J; `System.out.println` / `printStackTrace` запрещены.

## 3. Принципы ООП

### Инкапсуляция
- Поля классов — `private`; доступ наружу — через геттеры (Lombok `@Getter`), мутация — только там,
  где она реально нужна (`@Setter` осознанно: у DTO его нет вовсе, у сущностей есть — для JPA).
- Внутреннее состояние не раскрывается: наружу отдаются копии/DTO, а не ссылки на внутренние коллекции.

### Наследование
- Наследование используется только там, где есть настоящая is-a связь и переиспользование
  полиморфного поведения: адаптация Spring-интерфейсов (`CustomUserDetailsService implements
  UserDetailsService`), `UserAuthenticationToken extends AbstractAuthenticationToken`.
- Наследование ради переиспользования кода запрещено — для этого композиция (см. ниже).
- Ошибки — не иерархия классов, а данные: один `DomainException` с enum `ErrorCode`.
- Сущности не наследуют друг друга без отображения в JPA-стратегию (`@MappedSuperclass` и т.п.).

### Полиморфизм
- Общий код зависит от абстракции и не ветвится по конкретным типам: `GlobalExceptionHandler`
  ловит `DomainException` и получает статус и сообщение полиморфно через `ErrorCode`.
  Поддерживай этот принцип: вместо `switch` по типу добавляй поведение в сам тип.
- Работа с Security-контрактом — через интерфейсы Spring (`UserDetailsService`,
  `PasswordEncoder`, `AuthenticationManager`), а не через конкретные классы.

### Композиция и SOLID
- **SRP**: один класс — одна ответственность и одна причина для изменения. Сервис разросся
  на несколько зон ответственности — выдели отдельный сервис (`AuthService`/`RefreshTokenService`).
- **OCP**: новое поведение добавляется новым классом/кодом ошибки/бином, а не правкой
  ветвлений в существующем коде.
- **LSP**: реализация интерфейса обязана корректно выполнять контракт базового типа.
- **ISP**: интерфейсы узкие по назначению; «толстые» интерфейсы ради одного метода не создаются.
- **DIP**: верхние слои зависят на абстракции (интерфейсы Spring, `SecretKey`), конкретики —
  только в `config/`.
- Композиция предпочтительнее наследования: сервисы получают зависимости через конструктор,
  а не расширяют базовые классы с логикой.

## 4. Безопасность (обязательные инварианты)

- Пароли — только хеш через `PasswordEncoder` (`DelegatingPasswordEncoder`, по умолчанию `{bcrypt}`);
  открытые пароли не логируются и не попадают в DTO-ответы.
- Новые эндпоинты по умолчанию считаются защищёнными; публичными (`permitAll`) объявляются только
  маршруты аутентификации `/api/v1/auth/**` (и служебный `/error`).
- Проверки прав — `@PreAuthorize("hasRole('…')")` по enum `Role` (`ADMIN`, `OPERATOR`);
  ограничение «только свой клиент» для оператора — в сервисе (как `StagePolicy`), не в контроллере.
- Секреты и сроки жизни токенов — только из конфигурации (`jwt.*`).
- Вызовы kcr-ml — только через домен `ai/`: внутренний сервисный токен берётся из конфигурации
  (`app.ml.internal-token`), токены пользователя, ticket'ы и секреты не логируются.
- Данные, пришедшие из запроса, не интерполируются в SQL и не попадают в URL/`href` без проверки.

## 5. Проверка перед завершением работы

1. `./gradlew build` — успешно (нужен запущенный PostgreSQL стенда, §7/§8 ARCHITECTURE.md);
   если запускал только часть тестов, прогони интеграционные тоже — юнит-тесты не ловят
   проблем со схемой и посевом данных (пример — п. 38 §10). Если проект не собирался до тебя —
   не ухудшай состояние и явно сообщи об этом.
2. Новые классы лежат в правильных пакетах, имена соответствуют §2, зависимостей между слоями
   в обратную сторону нет (§1).
3. В изменённых Java-файлах, миграциях, `Dockerfile` и `application*.yaml` нет комментариев (§2).
4. Если изменены архитектура/модель/стек — ARCHITECTURE.md обновлён (§0).
5. В итоговом ответе перечисли изменённые файлы и результат сборки/тестов честно, без приукрашивания.
